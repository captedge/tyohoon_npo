# devlog: 地図表示・距離計算・データ取得方式の設計

宣言2（記録の4分割）の③を担当。以前のチャット（プロジェクト作成前）で3往復以上検討した内容をここに退避する。結論はCLAUDE.mdの「現状の要約」に1〜2行で反映済み。

## 経緯

1. **初期案**：オフライン前提・手動入力スタイル。船位置はCSV/Excelまたは地図タップで手入力。台風情報はJMA・JTWC（米軍）・WNIのテキスト/PDF/画像を見ながら人が緯度経度・日時を転記する共通フォームに入力する方式を検討。
2. **距離計算の方式検討**：当初は大圏距離（Haversine）を想定していたが、対象範囲が北海道〜フィリピン程度に限定されること、大まかな距離感の把握が目的であることから、実務でも馴染みのある**中分緯度法（Mid-Latitude Sailing）**を採用することにした。
   - 計算式：ΔLat（分）、ΔLong（分）、中分緯度 Lm=(Lat1+Lat2)/2、東西距離 Dep=ΔLong×cos(Lm)、距離（海里）=√(ΔLat²+Dep²)
3. **地図表示の方式検討**：本格的な地図タイル（MBTilesの事前ダウンロード）は実装コストが高いため、簡易プロット版（緯度経度グリッド＋簡易海岸線をCustomPainterで自前描画）を採用。表示範囲を北緯20°〜50°・東経115°〜150°に固定することで、座標変換をシンプルにし、海岸線データも該当範囲のみに絞れる。ズーム/パンは`InteractiveViewer`でラップして対応。
4. **手動読み取りの精度検証**：JMA画像はグリッド線があるため目視読み取りでも±0.5度程度の誤差で済むが、それでも緯度0.5度＝約30海里に相当し、無視できない誤差と判明。WNI画像はグリッド線がなく海岸線の形状から推測するため±1〜2度とさらに誤差が大きい。
5. **データソースの再検討**：手動読み取りの誤差が大きすぎるため、オフラインへのこだわりを一旦外してAPI取得を再検討した。
   - **気象庁**：正式な「台風API」は存在しないが、「防災情報XML」という無認証・無料の電文フィードに台風の位置・進路情報が含まれる。公式保証はなく仕様変更リスクはあるが、個人利用・低頻度アクセスであれば現実的。
   - **WNI**：台風情報を含むAPIは商用サービス「WxTech Data」（要見積もりの有料）。個人利用の無料枠は期待できないため不採用、画像による補助確認のみに留める。
   - **JTWC（米軍）**：既に使っているテキスト警報ページ自体が無料公開されているため、API不要でページ取得（定期フェッチ）で足りる。
6. **オンライン/オフラインの折衷案**：「常時オンライン」ではなく「Wi-Fiがある時（出港前・寄港中）にJMA防災情報XML＋JTWCテキストをまとめて取得してキャッシュ→船上ではキャッシュデータをオフラインで使う」ハイブリッド方式を採用。精度・手間・費用のバランスが最も良いと判断した。

## 追記：モックアップレビューによる表示範囲の見直し（2026-07-26）

簡易プロット版のモックアップ（グリッド線・仮の海岸線・船/台風アイコン・時刻スライダー）を提示したところ、以下のフィードバックを得た。

- 表示範囲は当初「北緯20°〜50°・東経115°〜150°」で決定していたが、フィリピンの主要な島々は北緯5°〜19°付近にあり、この範囲だとルソン島北端しか映らないと指摘があった。以前のチャットで話していた「フィリピンをカバーする」という前提と食い違っていたため、南側を「北緯5°〜50°」まで拡張することで合意（東経は115°〜150°のまま）。
- 縦方向の範囲が広がる分、初期表示は縮小して全体を見せ、ズームで拡大する形にする。
- 経度・緯度いずれもグリッド上に表示する（経度のみ見落とされていたため明示）。
- ズーム操作は`InteractiveViewer`のピンチ/マウスホイールに加え、＋／－ボタンとスライダーのUIも用意する。
- 表示ラベルは全て英語表記（国名・船・台風・時刻等）。
- 再生ボタンはトグル式（再生中に押すと一時停止）。

## 追記：投影法・表示比率の見直し、海岸線データの実データ化（2026-07-26）

Windows実機での初回動作確認後、続けて2つの見た目改善に着手した。いずれも複数往復のやり取りを経た設計変更のため、経緯をここに残す。

### 投影法（等角経緯度図法 → Web Mercator）

- **指摘内容**：実機でアプリを見たユーザーから「メルカトル図法に対して緯度経度のグリッド比率が悪く、日本の形が縦に縮んで見える」との指摘があった。
- **原因の特定**：それまでの実装は緯度・経度をそれぞれ独立にウィジェットの幅・高さへ線形マッピングする単純な等角経緯度図法だった。経度方向の実距離は緯度が高くなるほどcos(緯度)倍に縮むが、この補正がなく、かつ地図の描画サイズがウィンドウの形（アスペクト比）に応じてそのまま伸縮していたため、中緯度地域（日本など）の形が実際より東西に間延びして見えていた。
- **検討した対応方針**：ユーザーからは「再ズームアウトで上下が画面外に出てもよいので、見栄えの良い比率を常に表示したい。起動時は北緯30°・東経135°付近を中心にできないか」という要望があった。これを受けて、(1)投影法をWeb Mercator（Google Mapsと同じ、地図として見慣れた形になる）に変更、(2)表示範囲（N5-50/E115-150）のMercator換算での正しい縦横比を持つ**固定サイズの論理キャンバス**を導入し、ウィンドウ形状に関わらず地図の形が伸縮しないようにする、(3)起動時は範囲全体を縮小表示するのではなく日本付近を中心にズームインした状態で始める、の3点で対応することにした。
- **実装**：`lib/utils/map_bounds.dart`をWeb Mercator投影＋固定キャンバス（`MapBounds.canvasSize`、幅900×高さ約1360）に書き換え、`InteractiveViewer`は`constrained: false`でこの固定キャンバスをズーム・パンする方式に変更（`lib/screens/map_screen.dart`）。

### 海岸線データの実データ化

- 同じタイミングで、それまで仮のお絵かきレベルだった海岸線を実データに差し替えたいという要望があった。「技術的に問題なければ精度を高めたいが、今出なくても良い」という優先度の低い付帯要望も含まれていた。
- Natural Earth 1:50m/1:10mの詳細データを取得しようとしたが、このセッションで使える`web_fetch`ツールには1回あたりの取得サイズ上限があり、生のGeoJSON版はいずれもサイズ超過でパース不能（`json.loads()`失敗）だった。国別分割データ等の代替も試したが精度面で有意な改善はなかった。
- 最終的に、より軽量な`world-atlas`パッケージのTopoJSON版1:110mデータ（55KB）を採用。TopoJSONのアークを手書きデコーダーで復元し、表示範囲でクリップ・簡略化して`assets/coastline/coastline.json`として同梱した。
- **高精細化の道筋**：ユーザーが`naturalearthdata.com`から1:50m/1:10mデータを直接ダウンロードしてプロジェクトフォルダに置けば、Coworkはローカルファイルとして読み込めるためサイズ制限を回避できる。優先度低のためユーザー判断待ち（`TASKS.md`参照）。

## 教訓（次回同じ状況で使える判断基準）

- **目視でのグリッド読み取りは「大まかな距離感」用途であっても誤差が大きすぎる場合がある**：緯度0.5度は約30海里に相当し、台風接近時など緊急性が高い状況では無視できない。精度が必要な数値は、多少実装コストがかかってもデータソース側（API・電文フィード等）から機械的に取得する方を優先する。
- **「公式API」という名称にこだわらず、無料公開の電文フィード・テキストページも実用的なデータソースになりうる**：気象庁の「防災情報XML」やJTWCのテキストページのように、正式なAPIとして提供されていなくても、無認証・無料でアクセスできる公開データがあれば、個人利用・低頻度アクセスの範囲では十分実用に耐える。ただし公式保証がない分、仕様変更リスクは残ることを認識しておく。
- **オフライン要件とデータ精度はトレードオフになりがち**：「常時オフライン」に固執せず、「電波がある時にまとめて取得してキャッシュ」というハイブリッド方式にすることで、両立できる場合がある。
- **対象範囲が限定的な用途では、大圏距離のような汎用的だが複雑な計算式より、中分緯度法のような実務に即したシンプルな計算式で十分なことが多い**。
- **表示範囲などの「対象エリア」を決める際は、以前の会話で言及した地名（例：フィリピン）が実際にその緯度経度範囲に収まっているかを地図モックアップ等で機械的に確認してから固定する**。「〇〇が入れば十分」という言葉だけの合意は、実際の緯度経度と照合しないと範囲がずれる（今回はフィリピンの大半が北緯20°未満にあることを見落としていた）。
