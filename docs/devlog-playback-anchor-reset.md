# devlog: 再生位置（_startTime/_offsetHours）が意図せずリセットされるバグ

宣言2（記録の4分割）の③を担当。同一テーマで2回の修正往復が発生し、1回目の修正方針が「もっともらしいが不十分」だった典型例のため、次回同種のバグに再利用できる判断基準として退避する。

## 症状（ユーザー報告、2026-07-29）

Informationダイアログで台風のDisplay設定（JTWC/JMAのOn/Off）を変更してSaveすると、再生中・ポーズ中を問わず再生位置（時刻スライダー）が先頭（`_offsetHours = 0`）に戻ってしまう。

- 1回目の報告：「同じ台風でJTWCのみ表示中に再生・ポーズし、そこでJMAを表示させると再生位置が先頭に戻る（逆も同様）」
- 1回目の修正後の再報告：「JMA表示→途中からJTWC表示：OK／JTWC表示→途中からJMA表示：まだ先頭に戻る」

## 原因（共通）

`map_screen.dart`の`_showLabelSettingsDialog`のSaveハンドラは、スロット0の警報から再生開始時刻（`_startTime`）を解決し直す仕組みを持つ（2026-07-28実装、「読み込んだ情報の発表時間」を再生開始時刻とする仕様）。

```dart
final newStartTime = slot0Jma.isEmpty
    ? parsedJtwc[0]?.issuedAtJst(DateTime.now())  // JTWCベース
    : (slot0Jma.observedAtJst ?? slot0Jma.reportDateTimeJst);  // JMAベース（JMAがあれば優先）
```

この`newStartTime`は「JMAデータがあればJMA優先、無ければJTWC」という優先順位で**毎回のSaveで再計算**される。Display欄のチェックボックスを変えるだけでSaveを押しても、この計算式自体は必ず実行される。

## 1回目の修正（不十分だった）

「`newStartTime`が`null`でなければ無条件にリセット」という当初の実装がそもそも荒すぎたため、まず「解決後の値が現在の`_startTime`と実際に異なるかどうか」で判定するよう変更した：

```dart
if (newStartTime != null && newStartTime != _startTime) { ... リセット ... }
```

これは「JMA表示→途中からJTWC表示」のケースには効いた：スロット0が最初からJMAデータを持っていた場合、`newStartTime`は常にJMAベースの同じ値に解決されるため、JTWCのDisplayを変えるだけなら値は変わらず、リセットされない。

しかし「JTWC表示→途中からJMA表示」では直らなかった。原因：JMAを**初めてFetch**すると、優先順位ルールにより`newStartTime`の算出根拠がJTWCベースからJMAベースへ**切り替わる**。JTWC由来の時刻とJMA由来の時刻は別々の実データ（別の電文・別の警報）から来ているため、たとえ「同じ台風の同じ実況」を指していても、解決後の値はほぼ確実に異なる。結果、「値が変わった＝ユーザーが意図した更新」という前提が崩れ、依然として誤ってリセットされていた。

## 2回目の修正（根本対応）

判定基準を「解決後の値が変わったか」から「**その時点で再生のアンカーになっているソース自体の生データが変わったか**」に変更した。

```dart
final previousJma = _typhoonSlots[0].jmaInfo; // このSave直前の値
final anchorSourceChanged = previousJma.isEmpty
    ? typhoonControllers[0].text != _typhoonSlots[0].pastedText // JTWCが基準だった
    : !identical(slot0Jma, previousJma); // JMAが基準だった（Fetchで別オブジェクトになったか）
```

- 直前にJMAデータが無かった（＝JTWCが基準だった）場合は、JTWCの貼り付けテキストが変わったかだけを見る。
- 直前にJMAデータが既にあった（＝JMAが基準だった）場合は、`jmaFetched[0]`が今回のSave内でFetchボタンにより新しいオブジェクトに置き換わったかだけを見る（`JmaTyphoonInfo`に値等価の`==`実装は無いため、`identical`による参照比較がそのまま「今回Fetchが実行されたか」の正確な判定になる——`jmaFetched`はダイアログを開いた時点で`_typhoonSlots[i].jmaInfo`をそのまま代入しているため、Fetchしない限り同一オブジェクト）。

これにより「JTWCで再生中にJMAを初めてFetchして追加する」ケースでも、JTWC側のテキストが不変である限りリセットされない。JMA側の軌跡は絶対時刻（JST）をそのまま保持する設計（`JmaTyphoonInfo.toTrackPoints()`、`docs/data-format-notes.md`参照）のため、`_startTime`を動かさなくてもJMAの軌跡は正しい位置に表示される——これが「アンカーを動かさなくても安全」と言える技術的な裏付け。

## 教訓（次回同じ状況で使える判断基準）

- **複数のデータソースに優先順位（フォールバック）があり、どちらが「採用されるか」が状況によって切り替わる設計では、「解決後の最終値が変わったか」で差分判定してはいけない。** 優先ソースが切り替わっただけで最終値は必ずと言っていいほど変わるため、「実際にユーザーが変更した」ケースと「採用元が切り替わっただけ」のケースを区別できない。
- **正しい差分判定は、「その時点で採用されている（あるいは採用されようとしている）ソースそのものの生入力が変わったか」を見ること。** 優先順位ロジックの外側で判定するのではなく、優先順位ロジックが「どのソースを見るか」を決めた後、そのソース自身の入力だけを比較する。
- **値等価の`==`を持たないオブジェクト（今回の`JmaTyphoonInfo`）を「変更されたか」の判定に使う場合、フィールド単位で手動比較するより、「同じ参照かどうか（`identical`）」が実は最も正確な判定になることがある。** 今回は「取得し直したら新しいオブジェクトになる」という設計（`jmaFetched[i] = jma;`で新規代入）と組み合わさることで、`identical`が「今回のダイアログ操作でFetchボタンを押したか」を過不足なく表現できた。
- **1回目の修正で「もっともらしく、片方のケースだけ直る」対応をしてしまった場合、それは往々にして「根本原因の一部だけを潰した」状態であることが多い。** 今回のように症状に方向性（A→B方向はOK、B→A方向はNG）がある場合は特に、両方向を機械的に机上でシミュレーションしてから「直った」と報告すべきだった（実際には2回ともユーザーの実機確認で見つかった）。次回は、修正の根拠となるロジック（今回で言えば優先順位の分岐）が絡む場合、両方向の分岐を意識的にトレースしてから報告する。
