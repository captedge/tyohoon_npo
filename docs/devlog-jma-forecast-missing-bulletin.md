# devlog: JMA自動取得が予報の無い暫定電文を掴み、予報軌跡が消えるバグ

宣言2（記録の4分割）の③を担当。同一テーマで3往復以上のやり取りが発生し、1回目の結論（「JMA側の発表仕様であり不具合ではない」）が誤りだった典型例のため、次回同種の調査に再利用できる判断基準として退避する。

## 症状（ユーザー報告、2026-08-04）

JMA由来の台風情報（Typhoon 1、2613TY DOLPHIN）で現在位置は表示されるが予報軌跡（予報円・将来位置）が無く、再生バーを動かしても位置が変わらない。台風が2つ同時に発表されている状況。

## 1回目の調査・結論（誤りだった）

- `lib/utils/jma_xml_parser.dart`を確認し、パーサー自体はXMLの`予報`ブロックをそのまま反映する作りで、パース側の不具合は無いと判断。
- 原因切り分け用に`lib/screens/map_screen.dart`のForecastダイアログへ予報点数表示（`N forecast point(s)`）を追加。ユーザー確認で「0 forecast point(s)」と判明。
- ここで「JMA発表の5日予報は番号付き台風または24時間以内に台風化見込みの熱帯低気圧に限られる」という一般的な発表ルールを根拠に、「TYクラスでもこの状況は起こりうる、JMA側の発表仕様でコード側の不具合ではない」と結論した。

**この結論は誤りだった。** 2613（DOLPHIN）はテレビでも報道されるほどの「非常に強い」台風であり、ユーザーが提示したJMA公式サイトの画像では、同時刻帯にはっきりと予報円・予報軌跡が表示されていた。一般的なルールへの当てはめだけで、目の前の具体的な台風（数日前から予報が正常に取得できていた実績のある台風）についての反証（本当にJMAが予報を出していないのか）を確認せずに結論を出してしまった。

## 2回目の調査・原因

ユーザーからJMA公式サイトのスクリーンショット（17:45発表、予報軌跡あり）の提供を受け、アプリの取得時刻（Cached: 17:01、電文自体の実況時刻は17:00）と突き合わせたところ、**アプリが取得した電文はJMAが出した「予報付きの正式発表」ではなく、それより新しい実況専用の暫定発表だった**可能性が高いと判断した。

`lib/utils/jma_feed_fetcher.dart`の`_findVptw60Urls`はフィードの`<title>`が「台風解析・予報情報」を含むかどうかだけで絞り込んでおり（コード自身のコメントで「意図的に緩い絞り込み」と明記済み）、`fetchLatestJmaTyphoon`／`fetchActiveJmaTyphoons`はいずれもこのタイトル一致で見つかった最新の電文をそのまま採用していた。正規の3時間毎・予報付き発表と、実況のみの暫定発表が同じタイトルパターンを共有し、後者が前者の直前に割り込むと、予報無しの電文を掴んでしまう構造だった。

## 対応

`fetchLatestJmaTyphoon`／`fetchActiveJmaTyphoons`の両方に、最新電文に予報が無い場合は`_jmaIdentity`（eventID→号数+名称→URLの順）で同一台風と判定できる範囲でフィードを遡り、予報付きの電文が見つかればそちらを優先する処理を追加。予報が本当に存在しない台風・熱帯低気圧は従来どおり実況のみで表示される。Agentツール（general-purpose）による独立レビュー実施——must-fix指摘なし。ユーザーがWindows実機で確認し、予報軌跡が正常に表示されることを確認済み。

## 教訓（次回同じ状況で使える判断基準）

- **「一般的な仕様・ルール」を根拠に「これは仕様であり不具合ではない」と結論する前に、目の前の具体的な事象がその一般ルールに本当に当てはまるかを、可能な範囲で反証を探してから結論を出す。** 今回は「TYクラスでも予報が無いことがある」という一般論に頼ったが、対象の台風が「数日前から予報を正常取得できていた実績のある、報道されるレベルの顕著な台風」であるという具体的な事実と照らせば、一般論への当てはめが弱い説明であることは、結論を出す前の時点で気付けたはずだった。
- **このアプリの目的にとって重要な機能（今回で言えば予報軌跡——台風と船の位置関係を示すという、このアプリの存在意義そのもの）が突然消えたという報告は、外部要因（データ提供元の仕様）で一見説明がついても、より高い基準で自己検証してから結論を出す。** サンドボックスから最新のJMAデータを直接確認する手段が限られていた（`web_fetch`が古いキャッシュを返す既知の制約）ことも一因だが、その制約自体を「確認できないので仕様だと判断する」の理由にせず、「確認できない範囲は結論の確信度を下げて伝える」べきだった。
- **フィードの絞り込みが「タイトル文字列の緩い一致」に依存している場合、同じタイトルパターンを共有する複数種類の発表（今回で言えば予報付き定時発表と実況専用の暫定発表）が存在しうることは、実装時点のコード自身のコメントで既に自覚していた（「意図的に緩い絞り込み」）。フィードベースの「最新1件を採用」ロジックでは、"最新である"ことと"欲しい種類の発表である"ことは別の条件であり、後者の判定（今回は予報の有無）をフィルタ条件に組み込む設計を実装時点から検討すべきだった。
