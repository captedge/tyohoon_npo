# 新規プロジェクト立ち上げ時の教訓集（持ち運び用）

**位置づけ**：このファイルは特定のプロジェクト（Seafarer's Certificates）に紐づく記録ではなく、`docs/project-declarations.md`（5つの運用宣言）を実際のセッションで初めて適用してみて見つかった、具体的な穴とその対策をまとめたもの。次に新規プロジェクトを立ち上げるときは、このファイルごとコピーして持っていく。

**使い方**：新しいプロジェクトを始めて`project-declarations.md`を渡すときに、このファイルも一緒に渡す。「セッティングフェーズで機械的に確認すべきこと」のチェックリストとして使う。

---

## 見つかった問題と対策

### 1. フォルダ名に日本語・アポストロフィが残っていた

- **原因**：過去プロジェクト（Ship's Time）で「プロジェクトパスは半角英数字のみ、日本語・アポストロフィがDart解析サーバーやaaptを壊す」という教訓が既にあったが、新規プロジェクトのフォルダを作る時点ではこの教訓が自動的にはチェックされなかった。
- **対策**：新規プロジェクト開始直後に、教訓が使い回せる技術（Flutter等）を使う場合は、フォルダパスが要件を満たすかを最初に確認・是正してから着手する。今回は英数字のみのサブフォルダ（`seafarers-certificates`）を新設して対応した。
- **汎用化した教訓**：「前のプロジェクトで踏んだ地雷」は、次のプロジェクトで自動的には避けられない。着手前に明示的にチェックする一手間が要る。

### 2. git初回セットアップで`user.name`/`user.email`未設定エラー

- **原因**：新しいリポジトリの初回コミットで、gitのグローバル設定（本人確認情報）がまだ入っていなかった。
- **対策**：`git config --global user.name` / `user.email`を設定してから再実行。
- **汎用化した教訓**：新規リポジトリの初回コミット手順には、認証・本人情報設定の確認ステップを最初から含めておく。

### 3. `commit.bat`が`git add .`のままだった（過去プロジェクトのルール逸脱）

- **原因**：雛形作成時に汎用的な`git add .`をそのまま書いてしまい、Ship's Timeで確立していた「変更した具体的なファイルのみを毎回明示的に列挙する」というルールを移植し忘れた。ルールの「存在」は知っていたが、実際のファイルへの反映を怠っていた。
- **対策**：`commit.bat`と`docs/operation-rules.md`の両方に「`git add .`は初回コミット以外禁止、Claudeが毎回変更ファイルを明示列挙する」ことを明記。
- **汎用化した教訓**：過去プロジェクトのルールを「知っている」ことと、新規プロジェクトの実ファイルに「実装されている」ことは別。雛形作成時は、テンプレート的に流用した設定ファイル1つ1つが、過去の教訓を本当に反映しているか個別に確認する。

### 4. 運用ルールをCLAUDE.mdから別ファイルへ退避した際、参照漏れが起きた

- **原因**：ファイルを移動しただけで満足し、「次回セッションで実際に読まれる導線があるか」を機械的に検証せずに完了報告してしまった。
- **対策**：「完了報告前チェック」を新設。報告前に、機械的に確認できることは必ず確認する（例：チェックリストに参照先ファイルが明記されているかをGrep/Readで確認）。報告文には「確認済み：〇〇」の形で検証内容を明記する運用にした。
- **汎用化した教訓**：ファイル整理・ルール移動などの「置き場所を変える」作業は、移動後に参照が生きているかの確認とセットでなければ完了ではない。

### 5. 運用ルールの土台（宣言書）自体がセッション開始チェックリストに入っていなかった

- **原因**：CLAUDE.md本文では宣言書に言及していたが、「毎回これだけ実行」というチェックリストの実行手順としては明記されておらず、実質的に毎回読まれる保証がなかった。
- **対策**：セッション開始チェックリストに`project-declarations.md`を読む手順を明示的に追加。
- **汎用化した教訓**：「土台となるルール」ほど、本文中の言及だけでなく、実行手順（チェックリスト）に具体的な項目として落とし込まれているかを確認する。

### 6. 「第三者視点でのレビュー」の定義があいまいだった

- **原因**：宣言3「最終チェックは別の視点で行う」が、自己内省的な視点変更なのか、独立した第三者（サブエージェント）によるレビューなのかを明記していなかった。
- **対策**：`project-declarations.md`・`docs/operation-rules.md`双方に、「別の視点」にはAgent（サブエージェント）ツールの呼び出しを含むことと、自己レビューで足りる場合／サブエージェントを使うべき場合の判断基準を追記した。
- **汎用化した教訓**：「別の視点」「第三者」といった言葉は、AI自身の解釈に幅が出やすいため、具体的な実行手段（ツール名など）まで踏み込んで定義しておく。

### 7. 役目を終えたブートストラップ用ファイルが片付けられずに残っていた

- **原因**：初期セットアップ用の一時ファイル（コピペ用スニペット）を、内容がCLAUDE.mdへ反映された後も削除するルールがなかった。
- **対策**：反映済みと確認した上で削除。
- **汎用化した教訓**：セットアップ専用の一時ファイルは「使用後は片付ける」ことを、セッティングフェーズの最後の手順として明示的に入れておく。

### 8. セッション終了時のチェックが、開始時ほどの強制力を持っていなかった

- **原因**：開始時は箇条書きのチェックリスト化していたが、終了時のルール（CLAUDE.mdの肥大化確認等）は`docs/operation-rules.md`内の文章の1行に埋もれており、実行漏れが起きやすい形だった。
- **対策**：セッション終了時チェックリストを開始時と対称的な形でCLAUDE.mdに新設した。
- **汎用化した教訓**：「毎回やること」は、文章中に埋め込むのではなく、開始・終了とも同じ形式のチェックリストとして独立させる方が実行漏れを防げる。

### 9. 複数セッション構成で、CLAUDE.mdの自己言及表現が誤認識を招いた

- **原因**：CLAUDE.mdに「Cowork（**このファイルを読んでいるセッション**）」と書いていたが、この表現は複数セッションが同じCLAUDE.mdを読む構成では、どのセッションから見ても「自分」に当てはまってしまう。実際にPowerShell-Claude側のセッションがこの文言を読み、自分をCoworkだと誤認識して、本来Cowork側の責務（TASKS.md更新・completed-log記録・gitコミット）まで自分の仕事だと解釈してしまった。
- **対策**：自己言及（「これを読んでいるのはどちらか」）ではなく、客観的に判定できる実行環境の違い（例：Cowork専用ツールの有無、サンドボックスマウントパスの有無、Windows PowerShellから`claude`コマンドで起動したか）で「あなたはどちらのセッションか」を判定する記述に書き換えた。
- **汎用化した教訓**：複数セッション・複数エージェント構成で共有ドキュメントを書くときは、「これを読んでいるのは私」のような自己言及表現を避け、各セッションが自分の環境から客観的に判定できる基準（利用可能なツール、ファイルパスの形式、起動コマンド等）で役割を判定させる。この種の誤りは、実際に該当セッションで読み込ませて動作を確認する（宣言1・完了報告前チェック）まで気づきにくい。

### 10. Windows `.bat`ファイルをCoworkのサンドボックスから「実行検証できない」ことを理由に、既知の構文ミスを2回連続で見逃した

- **原因**：Coworkのサンドボックスは Linux 環境のため、`.bat`ファイルを実際に実行して動作確認できない。この構造的な制約を認識してはいたが、「実行できないなら仕方ない」という姿勢のまま、代わりに機械的にチェックできるはずの既知の落とし穴（改行コードがLF/CRLFか、`if(...)`のような括弧ブロックの中に別の括弧を含むテキストがないか）を事前に確認せず提示してしまい、ユーザーに2回連続でエラーを発見・報告させる結果になった。
- **対策**：「実行して確認できないファイル」を渡す前に、実行確認の代わりとなる静的チェックリスト（改行コードの確認、括弧ネストの確認、直書き日本語の有無）を必須の完了報告前チェック項目として追加し、報告文に「確認済み：〇〇」の形で何を確認したかを明記するようにした。
- **汎用化した教訓**：「このツールでは実行テストができない」という制約は、検証を省略してよい理由にはならない。実行できない分だけ、既知の落とし穴に対する静的チェックリストを事前に厳密に当てる、という代替の確認手段を用意する。特にシェルスクリプト・バッチファイル・設定ファイルなど、コード実行環境が納品先と異なるものを作る際は要注意。

## 効果が出た例（うまく機能した証拠として記録）

### 9. 「エラーが出てから直す」から「書く前に教訓と照合して未然に防ぐ」への変化

- **以前（Ship's Time時代）のパターン**：`commit.bat`を実行→日本語ファイル名絡みのエラー→「日本語が…修正します」→再実行、という後追い修正が多発していた。
- **今回**：削除した旧ファイル名が日本語だったため`commit.bat`に日本語を書きそうになった場面で、実行前に`docs/flutter-windows-env-notes.md`のルール7（bat内日本語禁止）と照合し、`git add -u`＋新規ファイルのみASCIIパスで個別指定という書き方に自分で修正してから提示した。ユーザーに実行してもらう前にエラーの芽を摘めた。
- **なぜ機能したか**：教訓が①具体的なファイルに書き出されており、②「完了報告前チェック」により実行前に照合するステップが仕組み化されていたため。教訓を書いただけでは再発防止にならず、「実行前に照合する」という手順とセットで初めて効果が出た。
- **汎用化した教訓**：このパターン（後追い修正→事前照合）の変化自体が、記録システムが機能している一番わかりやすい兆候。次回以降も、同じような「事前に防げた」場面があれば、ここに追記していく。

## 持ち運び用ファイルの構成

- `project-declarations.md`・本ファイル：技術スタックを問わず常に渡す（汎用）
- `flutter-windows-env-notes.md`：次が「Flutter × このWindows機 × Cowork」の組み合わせのプロジェクトの場合のみ、追加で渡す（環境・技術固有の内容のため）

## 次回、新規プロジェクトを立ち上げるときのセッティング手順（この教訓を踏まえた版）

1. `project-declarations.md`と本ファイルを最初に渡す（Flutter × 同じWindows機のプロジェクトなら`flutter-windows-env-notes.md`も渡す）
2. プロジェクトフォルダのパスが英数字のみか確認・是正する
3. CLAUDE.md／TASKS.md／docs（devlog-index.md／completed-log.md／operation-rules.md）を作成
4. セッション開始・終了の両方のチェックリストをCLAUDE.mdに用意し、「宣言書」「運用ルール詳細」を必ず両方参照先に含める
5. git初期化時は本人確認情報（user.name/email）の設定有無を先に確認する
6. commit.bat等、過去プロジェクトから流用する設定ファイルは、1つ1つ「過去の教訓が本当に反映されているか」を個別に検証する
7. 一通りできたら、「完了報告前チェック」（自己確認＋必要なら第三者＝サブエージェントレビュー）を実施してから完了報告する
8. セッティングフェーズ終了時に、使い終えた一時ファイルを片付ける
