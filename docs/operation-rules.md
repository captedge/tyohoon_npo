# 運用ルール詳細（CLAUDE.mdから参照・忠実に遵守）

CLAUDE.mdの肥大化を避けるためにこのファイルへ退避したが、内容は毎セッション・忠実に守ること（「参照型」＝置き場所の移動であって、優先度や拘束力が下がるわけではない）。

## 記録のルール（このファイルの肥大化防止・毎セッション守ること）

1. **CLAUDE.mdに書いてよいのは「今後の判断に必要な最重要事項」だけ**：環境構成、運用ルール（回避策の結論のみ）、実装状況の要約。1項目1〜3行程度に圧縮する。
2. **同じテーマで3往復以上のフィードバック修正が発生したら、その時点で`docs/devlog-<テーマ名>.md`に退避する**（見出し→経緯→末尾に「教訓」まとめの書式）。CLAUDE.md側には「結論1〜2行＋詳細はdevlog参照」のみ残す。
3. **セッション終盤に一度、CLAUDE.mdが肥大化していないか自己チェックする**（目安：150行 or 8,000文字）。
4. **完了タスクは`docs/completed-log.md`に記録する**：
   `**タイトル**（日付、コミットハッシュ、該当すればブランチ名）— 結論1〜2行。詳細は`docs/devlog-xxx.md`（devlogを作らない軽微な変更なら省略）。`
5. **完了記録を書く前に、devlogへの反映を確認する**：数値の根拠・試して却下した選択肢・次回同種作業で再利用できる判断基準を含む場合は、往復回数に関わらずその場でdevlogに追記してから、completed-log.md側には結論1〜2行＋リンクのみを残す。
6. **TASKS.mdは「未着手・進行中」と「決定待ち・要確認事項」だけに保つ**：チェックを付けた（完了した）タスクは、その場で`docs/completed-log.md`に1〜2行で記録し、TASKS.mdの本文（詳細な要望・対応内容の長文セクション）からは除去する。除去前に上記4・5の要領で完了記録・devlogへの反映を済ませておく。CSV/XML形式の調査結果のような「進行中タスクではなく参照資料」に該当する内容は、TASKS.mdやdevlogではなく`docs/data-format-notes.md`のような専用ファイルに切り出す。この整理を怠るとTASKS.mdが完了タスクの長文説明で肥大化し、宣言2（記録の4分割）の②（進行中タスク一覧）としての役割を果たせなくなる（2026-07-25、TASKS.mdが233行・約45KBまで肥大化した実例あり）。

## 完了報告前チェック（宣言1・宣言3の実践、毎回の完了報告で必須）

「後で気をつける」という会話上の宣言は機械的に検証できないため禁止。作業完了を報告する前に、必ず以下を実行し、報告文に結果を明記する。

1. **変更した全ファイルをReadツールで読み直す**（編集ツールの返り値を信用して終わらせない）。特にCLAUDE.md／TASKS.md／docs配下など、次回セッションで参照される運用ファイルは、変更後に実際どう読まれるかを確認する。
2. **「次回・別の場面で本当に機能するか」を機械的に確認できる場合は、必ず実際に検証する**（推測で「大丈夫なはず」と報告しない）。例：
   - ルールを別ファイルに退避した→ セッション開始チェックリスト側にそのファイルを読む手順が明記されているかをGrep/Readで確認する
   - 設定ファイルを変更した→ 実際に該当箇所をGrepし、変更が反映されているか確認する
   - コードを変更した→ 可能な範囲で構文チェックを行う（`flutter analyze`は既知のクラッシュ問題があるため使わない。`docs/flutter-windows-env-notes.md`参照）
3. **見た目・使用感・好みなど、実際に見ないと判断できない部分だけ**をユーザーへの確認事項として残す。
4. **報告文には「確認済み：〇〇」の形で、何を機械的に確認したかを1行明記する。** これにより、ユーザー側は「言葉だけの約束」か「実際に検証済み」かを報告文自体から判別できる。「確認済み」の記載がない完了報告は、確認をサボっている疑いがあると判断してよい。
5. **「第三者視点でのレビュー」には、Claude自身が視点を変えて見直す方法に加えて、Agent（サブエージェント）ツールを呼び出して独立したレビューを行わせる方法を含む。** 以下の場合は自己レビューだけで済ませず、必ずAgentツール（例：`code-reviewer`系や`general-purpose`）でのレビューを実施する：
   - 実装済みコードの品質・セキュリティ・設計判断など、間違いが実害につながる重要な変更
   - 同じテーマで3往復以上のやり取りが発生し、自己レビューでは見落としを繰り返している可能性がある場合
   - ユーザーから明示的に「第三者視点で」「レビューして」と依頼された場合
   軽微な変更（ドキュメントの誤字修正、TASKS.mdのチェック更新等）は自己レビューのみで可。
6. **Coworkのサンドボックス（Linux）では実行・ビルドして検証できないもの**（Flutterのビルド／実機・エミュレータでの動作確認、`.bat`ファイル等）を渡す前は、実行確認の代わりに以下を必ず行う：
   - コードは可能な範囲の静的チェック（構文・import漏れ・型の不整合など）を目視で確認する（`flutter analyze`は既知のクラッシュ問題があるため使わない。`docs/flutter-windows-env-notes.md`参照）
   - `.bat`ファイル等を渡す場合は下記「Windows専用ファイル納品前チェックリスト」を適用する
   - 報告文に「確認済み：〇〇（具体的な確認内容）」を明記した上で、「Windows機でビルド・エミュレーターまたは実機で確認してください」とユーザーに促す
   - 「実行できないので仕方ない」で済ませず、実行できない分だけ事前の目視チェックを厳密に行う

## 作業完了後のテスト運用

1つの実装作業が完了したら、ユーザーに「Windows機でビルドし、エミュレーターまたは実機で確認してください」と促す。詳細な起動手順はTASKS.mdまたは`TEST_WORKFLOW.md`（必要になったら作成）を参照。

## セッション構成

本プロジェクトは単一セッション（Cowork）で進行管理とコーディングの両方を行う（CLAUDE.mdの「環境構成」参照）。Flutterのコードはテキストファイルであり、専用GUIアプリの操作を要するBlenderプロジェクトのような複数セッション分業は不要と判断したため。

- ファイル内容の検証は必ずReadツール（Windowsパス）を使う。サンドボックス経由の読み取り（bash等）は内容がずれることがあるため、コマンド実行専用と割り切る。
- 大量削除・単一ファイル削除がサンドボックスから失敗する場合は`allow_cowork_file_delete`ツールで許可を得てから再実行する。

## git運用（テキストのみ管理、コミットはユーザートリガー方式）

git管理を開始する場合は以下の方針に従う（2026-07-25時点で未着手）。

- 対象は**テキスト系ファイルのみ**（CLAUDE.md／TASKS.md／docs配下／`typhoon_ship_tracker/`内のソースコード等）。ビルド生成物（`build/`等）・大容量アセットは`.gitignore`で除外する。
- **git commit／git pushは、ユーザーが「コミットして」と発言したときだけ動く**（Coworkのサンドボックスから勝手にcommitやpushはしない）。
- リモートを設定する場合、GitHubの認証情報はユーザーのWindows機側にあるため、**commitもpushも必ず`commit.bat`経由（またはユーザー自身のPowerShell操作）で行う**。Coworkのサンドボックスからは`git push`を実行しない（認証情報がないため）。
- 初回セットアップ時は`user.name`/`user.email`のグローバル設定有無を先に確認する。
- このWindows機での既知の落とし穴（`git add .`は初回コミットのみ、日本語ファイル名は`git add -u`＋新規ファイルのみASCIIパス個別指定、サンドボックスからの直接commit/pushは信頼できない、サンドボックスからの読み取り専用gitコマンドでもロックファイルが残留しうる等）は`docs/flutter-windows-env-notes.md`の「一般的な注意」5・6・7に集約。git導入時は必ず確認する。下記「サンドボックスからのgitコマンド実行によるロックファイル残留」も参照。

### コミット運用フロー（3ステップ、git導入後に使う想定）

1. ユーザーが「コミットして」と発言する
2. Coworkが`commit_message.txt`を準備する：`git status`／`git diff`でその時点の変更内容を確認し、要約したコミットメッセージを`commit_message.txt`（`.gitignore`済み、gitの履歴には残らない一時ファイル）に書き出す。**この`git status`／`git diff`実行後、下記「サンドボックスからのgitコマンド実行によるロックファイル残留」の再発防止ルールに従いロックファイル残留を確認する。**
3. ユーザーが`commit.bat`をダブルクリックする：`git add -A` → `git commit -F commit_message.txt` → `git push -u origin main`が一括実行される

### サンドボックスからのgitコマンド実行によるロックファイル残留（2026-07-27発生・対策済み）

**発生した問題**：Coworkのサンドボックスから、状態確認だけのつもりで`git status`（読み取り専用のコマンド）を実行したところ、出力に`warning: unable to unlink '.../.git/index.lock': Operation not permitted`という警告が出ていた。これはgitがコマンド実行中に一時作成する`.git/index.lock`を、終了時にgit自身が削除しようとして失敗したもの（サンドボックスからのファイル削除が権限エラーで失敗する既知の癖——`build/`等の削除失敗と同じ現象、`docs/flutter-windows-env-notes.md`参照——が`.git`配下でも起きた）。このとき警告を「サンドボックスからコミットしているわけではないから問題ない」と判断して放置し、削除しなかった。その後ユーザーが`commit.bat`をダブルクリックしたところ、残っていた`.git/index.lock`が邪魔をして`fatal: Unable to create '.../.git/index.lock': File exists`で失敗した（`allow_cowork_file_delete`でロックファイルの削除許可を得て除去後、2回目の`commit.bat`実行で成功）。

**教訓**：
- 残留ロックファイルは「誰が作ったか」に関わらず、その後のgit操作（サンドボックス側・Windows側どちらも）を全てブロックする。「自分はコミットしていないから無関係」という判断は誤り。
- 警告メッセージ（`warning:`で始まる行）が出た場合、内容を読んで軽視せず、その場で対応する。「後で気をつける」に相当する先送り判断は宣言1違反。
- 状態確認のためだけであっても、サンドボックスからのgitコマンド実行はロックファイル残留のリスクを伴う。可能な限り避け、必要な場合も`git status`/`git diff`/`git log`など読み取り専用コマンドに限定する（`add`/`commit`/`push`はそもそも実行しない、既存ルール通り）。

**再発防止ルール（必須）**：
1. サンドボックスから`git`コマンドを実行した場合は、警告の有無に関わらず、実行直後に`.git`配下に残留ロックファイルがないか機械的に確認する（例：`find "<repoパス>/.git" -name "*.lock"`。`index.lock`に限らず`HEAD.lock`／`refs/heads/*.lock`等も対象に含める）。
2. 残留が見つかった場合は、ユーザーに完了報告する前に`allow_cowork_file_delete`で削除許可を得て除去し、再度残留がないことを確認する。
3. 上記の確認を経てから、初めてユーザーに「commit.batを実行してください」と伝える。

### Windows専用ファイル（`.bat`等）納品前チェックリスト

**背景**：Coworkのサンドボックスは Linux 環境のため、Windowsの`.bat`ファイル等を実際に実行して動作確認することができない。この制約を理由に検証を省略してよいわけではなく、「実行できない分、既知の落とし穴を事前に目視でチェックする」ことが必須（完了報告前チェック項目6）。

`.bat`ファイルを新規作成・編集して渡す前に、必ず次を確認し、報告文に「確認済み：〇〇」の形で明記する：

1. **改行コードがCRLF（Windows形式）になっているか**：`xxd <file> | head -3`等で`0d0a`（CRLF）になっているか確認する。Write/Editツールの既定はLF（Unix形式）なので、`sed -i 's/\r$//; s/$/\r/' <file>`等で必ず変換する。
2. **`if`／`for`など括弧`( )`を使う複数行ブロックの中に、括弧を含むテキスト（echoの文言等）が入っていないか**：ブロック内のテキストに別の括弧が入ると構文エラーになる。複数行の`if (...)`ブロックはそもそも避け、`if 条件 goto :label` ＋ `:label` の形で書く。
3. **ファイル内に日本語（またはASCII以外の文字）を直接書いていないか**：Windowsのコードページ次第で文字化けし、コマンドが誤動作する恐れがある。可変のメッセージ等はUTF-8テキストファイル経由で渡し、`.bat`側は読み込むだけにする。
4. 上記1〜3をすべて確認した上で「確認済み：CRLF変換済み・括弧ネストなし・日本語直書きなし」のように報告文に明記する。

このチェックリストで防げなかった不具合が新たに見つかった場合は、この項目に追記する（宣言4：繰り返し検知）。
