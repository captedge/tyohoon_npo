# devlog: 今後の開発方針（オンライン化・スマホ対応）のプロジェクト構成検討

**ステータス：仮方針（変更可能性あり）。2026-07-28時点の合意内容。**

## 経緯

オフライン版（デスクトップ、CSVインポート・JTWC手動貼り付け）がひととおり満足のいく完成度に達したことを受け、次の2つの大きな開発フェーズ（①オンライン化＝気象庁「防災情報XML」の自動取得・Wi-Fiキャッシュ、②スマホアプリ化＝Android/iOS展開）をどう進めるか相談があった。

論点は「同じプロジェクト内でブランチを分けて進めるか、別プロジェクトとして分けるか」。ユーザーの懸念は次の2つ：
- 同一プロジェクト継続の場合：プロジェクトフォルダ・CLAUDE.mdが肥大化し、パフォーマンス（Claudeとのやり取りの処理コスト）が低下するのではないか
- 別プロジェクトにする場合：オフライン版で培ったノウハウ（地図描画・距離計算・CSV/JTWC解析等の共通ロジック）を活かせるか、デザイン・機能面で一貫性のある1つのアプリになるか

当初ユーザーは「ブランチは切るが、マージせず複数の完成形（オンライン版／オフライン版、デスクトップ版／スマホ版）を並行維持する」方向を検討していた。

## 判断の経緯

1. **Flutterは元々「1つのコードベース→複数プラットフォーム」を前提とした設計**であり、`lib/`配下の地図描画（`MapPainter`）・距離計算（中分緯度法）・CSV/JTWC解析・モデル類はデスクトップ／Android／iOSで共通利用できる。プロジェクトを分ける、あるいはブランチを分けてマージしない運用にすると、この共通部分が複製され「一方だけ直して他方に反映し忘れる」という形で一貫性が崩れるリスクが高いことを確認。
2. **「情報量が多すぎてパフォーマンス低下」の懸念は、ブランチ運用そのものとは無関係**と整理。gitブランチはポインタに過ぎずフォルダの実体サイズに影響しない。実際にコスト増の原因になるのはCLAUDE.md・docs配下の分量であり、これは既存の宣言2（記録の4分割）・宣言5（コスト意識）の運用（CLAUDE.mdは要約のみ、詳細はdevlog-*.mdへ）を今後も徹底することで対応可能と判断。
3. オンライン化について、ユーザーから「JMA XML自動取得は使うか使わないかユーザー任意の設定にできる」という案が出たことで、**「オンライン版／オフライン版」という別々の完成形ではなく、同一アプリ内の設定トグル（ON/OFF）として実装する**方針に収束。手動貼り付け（JTWC警報テキスト）は既存機能としてそのまま残し、自動取得OFF時・取得失敗時のフォールバックとする。
4. スマホ対応のUI方針について確認したところ、「機能は基本的に同一、UIは横向き固定、デザイン・見た目はできる限りデスクトップ版と一貫させたい」との回答。これにより、スマホ版は別UIとして作り直すのではなく、既存の画面構成・ウィジェットをできる限り再利用し、画面サイズ差分（レイアウト調整）・横向き固定（`SystemChrome.setPreferredOrientations`）・タッチ操作向けの微調整（ボタン/スライダーのタップ領域等）で対応する方針に決定。

## 合意した方針（サマリ）

- **プロジェクト構成**：同一プロジェクト・同一`main`ブランチを継続。複数の完成形を並行維持する運用は取らない。
- **ブランチ運用**：フェーズごとに一時的なフィーチャーブランチ（例：`feature/online-xml`、`feature/mobile`）を切り、Windows実機（フェーズ①）・実機/エミュレータ（フェーズ②）での動作確認後に`main`へマージする、通常のgit運用とする。ブランチの作成・切り替え・マージも、既存のgit運用ルール（`docs/operation-rules.md`：サンドボックスからはstatus/diff/logのみ、add/commit/pushはユーザー指示時に`commit.bat`経由）に準じて慎重に扱う。
- **オンライン化の実装形態**：気象庁「防災情報XML」の自動取得は、アプリ内の設定でON/OFFできる機能として実装する（別バージョンではなく1機能）。OFF時・取得不可時は既存のJTWC手動貼り付けにフォールバックする。
- **進める順序**：①オンライン化をデスクトップ版のまま完成させてマージ→②その後にモバイル対応（`flutter create --platforms=android,ios .`で雛形追加）に着手する。①で作るデータ取得・キャッシュ層は②でもそのまま流用する想定。
- **スマホUI方針**：機能・デザインは極力デスクトップ版と共通にし、画面構成の作り直しはしない。横向き固定。画面サイズ差分とタッチ操作対応のみ個別に調整する。
- **ドキュメント運用**：フェーズごとに`devlog-online-xml.md`・`devlog-mobile-flutter.md`等、テーマ別のdevlogを追加していく。Android/iOSのビルド環境の癖は`flutter-windows-env-notes.md`と同様の専用ファイルに切り出す（CLAUDE.md本体には要約1〜2行のみ追記）。

## 教訓（次回同じ状況で使える判断基準）

- 「プロジェクトを分けるか／ブランチを分けるか」という相談が来たときは、まず「①コードの再利用性・一貫性の問題」と「②ドキュメント肥大化によるやり取りコストの問題」を分けて考える。この2つは原因も対策も別物であり、混同すると「ブランチを分ければパフォーマンス問題が解決する／プロジェクトを分ければ解決する」といった誤った対応につながる。
- Flutter（および一般にクロスプラットフォームフレームワーク）を使ったプロジェクトでは、「プラットフォームごとに別プロジェクト・別ブランチで完成形を複数持つ」運用は、共通ロジックの複製・分岐管理コストに対して得られるメリットが小さいことが多い。まず「同一コードベース＋設定/プラットフォーム分岐」で実現できないかを検討するのが定石。
- 「オンライン／オフライン」のような機能追加は、「別バージョンを作る」のではなく「既存機能に設定でのON/OFFを足す」形に落とし込めないか、着手前に確認する価値がある（今回のケースでは、この転換が構成上の懸念をまとめて解消した）。
