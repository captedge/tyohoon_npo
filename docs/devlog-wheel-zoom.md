# devlog: マウスホイールズームの不具合調査

宣言2（記録の4分割）の③を担当。同一テーマで3往復以上のやり取りが発生したため退避。結論はCLAUDE.md/TASKS.mdには残さず、本ファイルに集約する。

## 経緯

1. **最初の報告（1往復目）**：マウスホイールでのズームアウトが最小ズームまで届かない。＋／－ボタンとスライダーでは問題なし。ホイールでのズームインは問題なし。
   - **原因の当初の仮説**：地図を`InteractiveViewer`でラップし、その外側に独自の`Listener(onPointerSignal: _handlePointerScroll)`を置いてカーソル位置基準のズームを実装していたが、`InteractiveViewer`自体もマウスホイールのスクロールイベントに対して内部で独自のズーム処理を行っており、同一イベントに対して両者が反応し`_transformationController`を奪い合っていると推測。
   - **1回目の対応**：`onPointerSignal`内で直接処理せず、`GestureBinding.instance.pointerSignalResolver.register(event, handler)`経由でハンドラーを登録する方式に変更（`PointerSignalResolver`は「登録された最後の1つだけが実行される」仕組みのため、`InteractiveViewer`より後に登録すれば上書きできるはずという想定）。

2. **2回目の報告**：「変化なし」。実機でのより詳細な挙動：スライダー位置としてはある程度までズームアウトできるが、その後は進まず、代わりに表示画像の左右位置を再調整するような挙動になる。
   - **原因の再調査**：`PointerSignalResolver`は「resolverに登録した者同士」でしか競合解決をしない。`InteractiveViewer`自身のホイール処理はresolverを使わず`Listener.onPointerSignal`で直接（無条件に）実行される実装になっているため、こちら側だけresolver経由に変えても`InteractiveViewer`側の処理は止まらず、結局二重処理が継続していたと判明。
   - **2回目の対応**：独自の`Listener(onPointerSignal: ...)`によるホイール処理を完全に撤去し、`InteractiveViewer`本来の処理（カーソル位置基準ズーム、`minScale`/`maxScale`で自動クランプ）にすべて任せる方式に変更。副作用として、`InteractiveViewer`が自前でホイールを処理するようになったため、`onInteractionEnd`のみで行っていた内部状態（`_zoom`/`_translation`）の同期ではホイール操作後に状態が古くなる問題が新たに起こりうると判断し、`_transformationController`に対して`initState`で永続的な`addListener(_syncFromController)`を登録する方式に変更（変更理由を問わず常に内部状態を最新に保つ）。

3. **3回目の報告**：ホイールでのズームアウトは、地図の東西端（115E/150E）がちょうど画面の左右端に達するところまでしか進まない（＝これは正常動作、`InteractiveViewer`本来の挙動として妥当）。一方、右側のスライダー/ボタンでは、そこからさらに余白（海の外側の空白）が出るところまでズームアウトできてしまい、3つの操作方法の限界が揃っていない、という指摘。
   - **原因の特定**：`InteractiveViewer`はデフォルトで`boundaryMargin`（既定`EdgeInsets.zero`）を持ち、ドラッグ・ピンチ・ホイールなど「ジェスチャー由来」の変換に対しては、キャンバスの外側に余白が生じる位置まではズームアウトさせない制約がかかる。数式で表すと、この制約下での実質的なズーム下限は「2つの倍率（幅基準・高さ基準）のうち**大きい方**」（＝どちらの軸にも余白が出ない"cover"フィット）。一方、＋／－ボタンとスライダーは`_transformationController`を直接書き換える自前の実装のためこの制約を受けず、「2つの倍率のうち**小さい方**」（＝片側の軸に余白が出ることを許容する"contain"フィット、キャンバス全体を必ず見せる方式）まで到達できていた。この2つの倍率の違いが不一致の直接的な原因。
   - **3回目の対応**：新設した`_coverFitScale`（cover＝大きい方の倍率）を＋／－ボタン・スライダーの下限（`_minZoom`）に採用し、ホイールの自然な限界と一致させた。起動時の初期ズーム計算（`_fitScale * 1.8`）は、意図しない見た目の変化を避けるため元の`_fitScale`（contain＝小さい方の倍率）のまま維持し、cover/containの2つの倍率を明確に分離して管理する設計にした。

## 教訓（次回同じ状況で使える判断基準）

- **`InteractiveViewer`を独自のジェスチャーハンドラーで囲む際は、`InteractiveViewer`自体が同じ種類の入力（特にマウスホイール）に対して独自の内蔵処理を持っていないか、実装前に確認する。** 「自分の処理を足す」のではなく「デフォルトの挙動を上書きする」つもりで設計しないと、同一イベントに対する二重処理が起きる。
- **`PointerSignalResolver`による競合解決は、双方がresolverを使っている場合にしか機能しない。** 片方が`Listener.onPointerSignal`で直接（無条件に）処理している場合、もう片方だけresolver経由に変えても無力。既存ウィジェット（Flutter SDK内蔵のもの含む）が内部でどちらの方式を使っているかは、公式ドキュメントだけでは分からないことがあるため、修正後は必ず実機で「本当に直ったか」を確認する（「理論上直るはず」で完了報告しない）。
- **既存のウィジェット（`InteractiveViewer`等）の挙動と競合する独自実装がある場合、最も安全な修正は「独自実装を撤去し、既存ウィジェット本来の挙動に一本化する」こと。** 部分的にオーバーライドしようとするより、責務を完全にどちらかに寄せる方がトラブルが少ない。ただし、独自実装が担っていた副次的な役割（今回は内部状態の同期タイミング）が失われないよう、置き換えの範囲を丁寧に洗い出す必要がある。
- **「ズームの最小値」のような一見単純な仕様も、実装方式（ジェスチャー経由か、変換行列の直接操作か）によって実際に到達できる限界値が異なりうる。** 複数の操作手段（ホイール／ボタン／スライダー）で同じ機能を提供する場合は、限界値の計算式が全操作手段で同じロジックを参照しているかを確認する。今回は「キャンバス全体を余白ありで収める（contain）」と「余白なく画面を埋める（cover）」という、似て非なる2つの「フィット」の概念を混同していたことが根本原因だった。
